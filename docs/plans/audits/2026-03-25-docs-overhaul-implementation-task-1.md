# Task 1: Create the gzip benchmark script — Audit Report

**Summary:** The benchmark script is well-structured and will run correctly against the provided JSON data. However, the plan description lists expanding `places[*].nearbyCity` but the code omits this expansion entirely. There are also missing expansions for `routes[*].hotelInfo.centerPlace` and direct array accesses without bounds checking. None of these would cause a crash with the current data, but they make the unnormalized size smaller than a truly unnormalized version, slightly deflating the benchmark results.

**Findings:**

| 1 | Incorrect Code | Amend Plan | **Plan description says to expand `places[*].nearbyCity` but the code omits it.** Line 59 says "For each place: replace `nearbyCity` (int) with full place object." The actual code (lines 87-255) never creates an `expandedPlaces` array — it uses the raw `places` array everywhere. The JSON has 21 places with `nearbyCity` references. When places are inlined into lines, routes, hops, and result, those `nearbyCity` fields remain as raw integers instead of full place objects. This underestimates the unnormalized size. | Plan lines 59, 87-255 | Add a `places[*].nearbyCity` expansion step before `expandedLines`. Create an `expandedPlaces` array where each place's `nearbyCity` (if present) is replaced with `places[nearbyCity].DeepClone()` (using the RAW `places` array, not the expanded one, to avoid recursion). Then use `expandedPlaces` instead of `places` in all subsequent lookups (lines, routes, result.originPlace, result.destinationPlace). |

**Overall assessment:** The script will run successfully and produce valid benchmark numbers. The two substantive issues (findings #1 and #3) should be addressed — #1 because the plan text explicitly calls for `nearbyCity` expansion but the code omits it, which would be noticed during review and makes the benchmark less representative; #3 because consistent use of the `Lookup` helper is low-effort and prevents confusing crashes.
