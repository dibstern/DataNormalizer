# Audit: Task 11 — Update all existing tests for root property change

## Summary

Task 11 is a sweeping test/sample update to reflect the new `Result` property on containers and the conditional removal of the root type's list property. The plan has **significant gaps**: it misses 4 files that need updating, provides insufficient guidance on which specific access patterns exist and how to handle them (there are at least 5 distinct patterns, not just `[0]`), and overlooks a critical upstream dependency bug in the `NeedsList` computation that could make circular reference test updates incorrect.

## Detailed Analysis by Category

### Insufficient Test Coverage

The task's file list misses **4 files** that contain `Dtos` patterns:
1. **`JsonNamingTests.cs`** — Tests JSON serialization output with `"personDtos"`, `"contactDtos"` property names. If root type no longer has a list property, the serialized JSON won't contain `"personDtos"` — it will contain `"result"` instead. This file has 8+ assertions that check for root-type list JSON names.
2. **`EmitterHelpersTests.cs`** — Tests `GetListPropertyName` which returns `"PersonDtos"`. The helper itself doesn't change, but test expectations may need updating if the helper is no longer called for root types.
3. **`DtoEmitterTests.cs`** — Appears safe (no `Dtos` list assertions), but should be explicitly verified.
4. **`GeneratorTests.cs`** — Appears safe (no `Dtos` access), but should be explicitly verified.

Additionally, there are NO `.verified.cs` or `.verified.txt` snapshot files in the repo, so snapshot breakage is not a concern.

### Implicit Assumptions

The plan assumes a simple `container.{RootType}Dtos[0]` → `container.Result` replacement, but the actual codebase has **5 distinct access patterns**:

1. **Index access**: `result.PersonDtos[0]` (11 occurrences) → `result.Result`
2. **Length check**: `result.PersonDtos.Length > 0` (4 occurrences) → REMOVE if NeedsList=false
3. **Has.Length constraint**: `result.UniverseDtos, Has.Length.GreaterThanOrEqualTo(1)` (1 occurrence) → REMOVE if NeedsList=false
4. **Variable assignment**: `var addresses = result.AddressDtos` (3 occurrences) → KEEP (non-root)
5. **Inline property access**: `personResult.PersonDtos[0].Name` (2 occurrences) → `personResult.Result.Name`

Pattern (2) is particularly dangerous: accessing `.Length` on a property that doesn't exist would be a compile error, but the plan only mentions "remove that assertion (or keep if root is referenced)" without clear guidance on how to determine which case applies.

### Fragile Code

The E2E tests (`GeneratorEndToEndTests.cs`) use string-searching in generated source code (e.g., `Does.Contain("PersonDtos")`, `Does.Contain("result.PersonDtos")`). These are fragile because:
- The same string `"PersonDtos"` could appear in different contexts (container property vs normalizer assignment)
- After the change, root types may have `Result` instead of `PersonDtos`, but non-root types still have their lists
- The test at line 441 does substring extraction between two `Normalize` method signatures, which is particularly brittle
