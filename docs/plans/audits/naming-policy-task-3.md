# Task 3: Extend ConfigurationParser to parse new config syntax — Audit Report

**Summary:** Task 3 has several significant issues. The most critical are: (1) the `Reference().JsonName()` chaining pattern fundamentally cannot work with the existing `GetUltimateReceiverName` architecture, which always resolves to the root receiver; (2) the plan underspecifies property assignment parsing — a brand-new code path is needed in `ProcessStatements` but the plan treats it as a minor addition to the existing invocation-based switch; (3) the `RootPropertyName` assignment on `JsonContractBuilder` has the same missing assignment-parsing problem as `NamingBuilder`.

The plan says `JsonName` should match on `ReceiverKind.ReferenceBuilder`, but the `receiverKind` will be `TypeBuilder` because `x` is what's in the ReceiverMap. ## Summary of Critical Amendments Needed

1. **Architecture change for cross-type chains** (Finding #1): The `GetUltimateReceiverName` approach cannot support `Reference().JsonName()`. The plan needs a concrete code-level solution, not just "add cases."

2. **New `ProcessAssignment` method** (Findings #2, #3, #5): Property assignment parsing is a fundamentally new code path in `ProcessStatements` that the plan underestimates. It needs its own method with explicit handling for string vs bool literals and multiple receiver kinds.

3. **`PropertyJsonNames` wiring gap** (Finding #8): Data flows into `ParseContext` but has no path to `NormalizationModel`.

4. **Graph-level naming merge semantics** (Finding #7): Design question that affects implementation approach.
