# Task 14: Add unparsed config statement diagnostics — Audit Report

**Summary:** The task has several significant design gaps. The proposed test case `n.DtoSuffix = GetSuffix()` will NOT produce a DN1001 diagnostic because the assignment is matched by the existing switch branch (not falling through to `default`). The plan's Step 5 is underspecified — it proposes storing `Diagnostic` objects (with `Location`) on `NormalizationModel` but doesn't address how to serialize those through the existing `GeneratorDiagnosticInfo` pipeline, which currently only carries `(Id, TypeName)` and uses `Location.None`. Additionally, the `BuilderLambdaDepth` increment/decrement sites are not enumerated, and only one of four lambda-processing methods currently uses try/finally.

## Category Summary

**State Issues:** Two findings (#5, #6) — `BuilderLambdaDepth` needs try/finally and explicit enumeration of all increment sites. Both require plan amendments.

**Incorrect Code:** Four findings (#1, #2, #7, #8) — A key test case (`n.DtoSuffix = GetSuffix()`) is fundamentally wrong, the file path for DiagnosticDescriptors is wrong, and the class redefinition approach is incorrect.

**Missing Wiring:** Two findings (#3, #15) — The diagnostic pipeline from ConfigurationParser through GeneratorOutput to Emit is underspecified and references a non-existent `.Execute()` method. `GeneratorDiagnosticInfo` needs to be extended.

**Implicit Assumptions:** Three findings (#4, #14, #16) — Storing `Diagnostic` objects vs data, expression-body lambda blind spot, and asymmetric diagnostic behavior between Configure body and lambdas.

**Insufficient Test Coverage:** Three findings (#10, #11, #12, #13) — Critical gap: many "recognized but unprocessed" statement patterns won't produce DN1001 diagnostics. The approach only catches truly unrecognized statement *types*, not recognized statements with unsupported content.

**Fragile Code:** One finding (#9) — `ToFullString().Trim()` can produce very long diagnostic messages.

---

## Critical Design Question

The most fundamental issue is **Finding #1** combined with **Findings #10 and #11**: The `default` case in `ProcessStatements` only catches statement *types* that don't match any case pattern (`IfStatementSyntax`, `ForStatementSyntax`, `ReturnStatementSyntax`, etc.). But many partially-understood statements — assignments with non-literal RHS, invocations of unknown methods on known receivers, local declarations with non-invocation initializers — are matched by existing cases, processed partially, and silently dropped when the sub-processing can't handle them. These "recognized but not fully processed" statements are arguably MORE dangerous than truly unrecognized statement types, yet the plan's approach won't flag them.

**Recommendation:** The plan should either (a) acknowledge this limitation explicitly and only target truly unrecognized statement types, adjusting test cases accordingly, or (b) redesign the approach so that processing methods return a `bool` indicating whether they successfully consumed the statement, and emit DN1001 when they return `false` inside a builder lambda.
